# Internationalization

## Languages and catalogs

lig supports English, Russian, and Spanish through [Fluent](https://projectfluent.org/). The
executable embeds `locales/en.ftl`, `locales/ru.ftl`, and `locales/es.ftl` at build time. The
application needs no external translation files at runtime.

The catalogs contain the window title, greeting, and application-authored startup diagnostics.
Backend names and raw operating-system or library error details retain their original form in developer diagnostics only.
The interface never displays these diagnostic entries. Follow [user-facing content rules](../rules/user-facing-content.md).

## Language selection

The application selects its language once at startup:

1. Use a nonempty `LIG_LANG` override when present.
2. Otherwise, read the native system locale through `sys-locale`.
3. Use English when the selected locale is unavailable or unsupported.

Region variants use their base language. For example, `ru-RU` selects Russian and `es-MX` selects
Spanish. Selection accepts case differences and POSIX forms such as `ru_RU.UTF-8`. An unsupported
explicit override selects English, even when the system locale supports another language. Child
processes inherit `LIG_LANG` without changing the parent environment.

On macOS or Linux:

```sh
LIG_LANG=ru make run
LIG_LANG=es cargo run --locked
LIG_LANG=en cargo run --locked
```

In Windows PowerShell:

```powershell
$env:LIG_LANG = "es"
cargo run --locked
Remove-Item Env:LIG_LANG
```

Restart the application after changing the override. The current interface has no language selector
or saved language preference.

## Implementation

`infrastructure::locale` reads the environment and native system locale. `i18n` selects a
supported language and formats Fluent messages. `main` creates one immutable localizer and shares it
with the application and graphics launcher. `Lig` keeps the localizer in application state. Views
request text through typed message keys. No global mutable language state exists. See
[the localization decision](../adr/0003-embedded-localization.md) for alternatives and consequences.

A missing, empty, or invalid selected translation falls back to English.
If that message also fails, the formatter uses the localized `message-unavailable` text.
If both catalogs fail, the formatter returns empty text without exposing internal identifiers.
Tests validate catalogs directly, so fallback cannot conceal catalog defects during CI.

## Adding text

1. Register a purpose-based key in `src/i18n/mod.rs`.
2. Add the message to all three `.ftl` catalogs.
3. Use `I18n::text` for static messages.
4. Use `I18n::format` with `FluentArgs` for messages with dynamic values.
5. Add an argument test case for the new key.
6. Check layout for all three languages when the message appears in the interface.

For example, each catalog defines `graphics-trying` with the same `$backend` argument. Fluent
inserts the backend name while preserving each language's sentence structure.

## Verification

Run `cargo test --locked i18n::tests` for catalog and language selection tests. Run `make
check` for all checks, including interface tests across languages. Tests check complete key sets,
syntax, arguments, independent localizers, fallback, titles, and greeting layout. See
[the mandatory i18n rules](../rules/i18n.md) for review requirements.
